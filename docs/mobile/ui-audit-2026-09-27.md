# Native mobile UI audit — 27 September 2026

The most urgent repair is the template modal: its header overlaps the iPhone
status bar and Dynamic Island, hiding the recipient and making Back unreliable.
The next priority is explaining older approved template formats instead of asking
staff to fill anonymous numbered fields. The app needs targeted repairs, not a
new navigation model or a visual redesign.

## Findings

Priority: **P1** impairs an important workflow; **P2** degrades daily use or
clarity; **P3** is lower-impact polish. Observations are distinguished from
source-only risks. No P0 issue was established.

### F01 · P1 · Template modal ignores the phone's safe areas

**Observed, steps 4–6.** Title and recipient draw behind the status bar and
Dynamic Island. The send bar occupies the bottom edge. Back could not be
activated through the mirror; reopening the app was needed to leave the editor.
The recipient must be readable before a send, and the exit must be reachable.

**Code:** `apps/mobile/src/features/inbox/components/template-picker.tsx:664`
renders a native `Modal` with `ScreenSafeAreaView`, but no modal-local provider.
`src/core/mobile-app-providers.tsx` provides safe areas at the app root only.
Provider placement is the leading hypothesis, not a measured root cause yet.
Measure modal insets and fix their ownership; do not add a guessed status-bar
height. Inspect the reaction modal for the same problem without assuming it fails.

### F02 · P1 · Older templates ask for “Message detail 1–4”

**Observed, steps 4–5; source-confirmed fallback.** The membership template offers
four anonymous fields and no name prefill; the list repeats those placeholders.
Staff must infer whether each blank means name, plan, date, or price. That is a
poor fit for a renewal workflow and can cause incorrect customer-facing copy.

**Code:** `template-presentation.ts:105` intentionally uses contract labels only
when the variable count matches. The 26 September changelog documents that
fallback. This is not evidence that all prefill is broken. The visible older
copy has four body values; the current membership contract has five, including
the legal business name.

Keep the guard. Introduce an explicit presentation/readiness outcome for a known
contract with a mismatched approved format: **Template needs an update**, with
clear owner/admin recovery on the website. Keep compatible templates available.
Do not infer positional meaning, silently change provider-approved text, or
reuse an older name as proof of current contract readiness. Custom templates
without a known contract need a separately defined manual-entry policy.

### F03 · P2 · Native navigation bars remain light in a dark app

**Observed, steps 7–8.** Account and App details show a large white navigation and
status-bar region over a black body. Returning to Chats restores dark chrome.

**Code:** `app/(app)/_layout.tsx:9` uses default Stack options. Root providers do
not provide a matching navigation theme. `app/(app)/photo.tsx` already explicitly
maps header colors to native tokens. Apply a coherent navigation theme at the
shared stack/provider boundary, including transition backgrounds and status-bar
content. Avoid separate Account and App details color patches.

### F04 · P2 · Chat preview length determines the entire row height

**Observed, step 1.** A renewal preview occupies four lines at the current text
size, while a nearby short preview occupies one. Longer actual messages can
expand much further. This makes scanning and reaching unread chats slower.

**Code:** `components/conversation-row.tsx:68` renders unbounded preview text.
Use a bounded preview at ordinary text sizes, with a deliberate large-text
layout. Preserve the prior accessibility fix: no fixed row height or blanket
font-scaling cap, and keep name/time/unread information available. Full content
belongs in the chat; assistive output must not lose the preview.

### F05 · P2 · Empty states confuse “all caught up” with “no chats”

**Observed, step 2.** All contains two chats; selecting Unread shows **No chats
yet / New WhatsApp chats will appear here**. That wrongly describes an established
inbox. Source uses the same state for an unsuccessful search.

**Code:** `screens/inbox-screen.tsx:89`. Distinguish empty branch, no unread chats,
and no query matches. Offer **Show all chats** or **Clear search** as appropriate
using existing masters. Preserve query/filter state unless the user clears it.

### F06 · P2 · The active branch is hidden on Chats

**Observed absence, steps 1 and 3; multi-branch impact inferred.** Chats shows
only UsefulDesk; a chat shows only the recipient. The branch can be checked only
in Account. This audit had one available branch, so it did not reproduce a
wrong-branch action, but the shared UI provides no orientation for multi-branch
staff either.

**Code:** `components/inbox-header.tsx:6` accepts only the Account callback.
Expose the current branch on the Chats home header and retain Account access,
with long-name/large-type reflow. Reuse the existing branch-selection flow
rather than adding another switcher. Conversation and template screens keep
their recipient-focused headers without repeating the branch name.

**Post-audit refinement:** this home-only placement is built and covered by
mobile tests. The final placement has not been reinspected on the physical
iPhone after the refinement.

### F07 · P2 · Delivery ticks can wrap away from their timestamp

**Observed, step 3.** The outbound support message places its timestamp on the
last text line, then strands the blue double tick on the next line at the left.
Delivery status no longer reads as one unit.

**Code:** `components/message-bubble.tsx:72` nests timestamp text and a separate
`DeliveryTick` View inside message text. Keep time and tick together as one
measured metadata unit; when it cannot fit, move the whole unit to a trailing
row. Preserve the existing separate-row accessibility-size behavior and failed
status announcements. Verify native wrapping, not just a JSX snapshot.

### F08 · P2 · Reply quote uses a web color token in the native theme

**Observed dark quote stripe, step 3; source confirms missing token.** The quote
bar is black and disappears into the dark inset rather than providing a clear
quote marker.

**Code:** `components/reply-quote.tsx:29` uses `border-l-primary`; the native CSS
and HeroUI theme expose `accent`, not `primary`. Use the existing native semantic
accent token in this shared quote component. Keep the familiar four-point quote
bar. This affects both persisted quotes and the composer's staged reply.

### F09 · P2 · Read-only and readiness states leave an unexplained blank footer

**Source-confirmed; not exercised with a viewer account.**
`screens/conversation-screen.tsx:711` returns no footer for viewer, inactive
branch, and loading. A staff member cannot distinguish their permission limit
from loading or a missing composer.

Reuse `Notice` to state **View only** or the branch restriction, and show a
concise loading state for readiness when appropriate. Keep send/reaction gates
and existing named authorization predicates unchanged; do not render unusable
composer controls just to explain their absence.

### F10 · P3 · Long diagnostic values break awkwardly

**Observed, step 8.** The Supabase host wraps its final character onto a separate
line in the right-aligned label/value row.

**Code:** `foundation/diagnostics-screen.tsx:98`. Stack long values under their
label when needed, including at large text sizes; preserve the complete host and
keep secrets excluded. This is support readability, not a reason to shorten or
hide the actual connection identity.

## What already works

- A simple chat-first stack, with no empty product tabs.
- The closed-window notice uses an outline state treatment and offers one clear
  template action. Preserve that hierarchy.
- Search and its scope share one compact control, matching an explicit existing
  mobile decision. There is no reason to restore a separate chip row solely to
  resemble another app.
- Shared native text, semantic chat colors, readable delivery labels, 48-point
  controls, failed-send handling, and uncertainty locks already exist in source.
  Keep them; this audit does not claim fresh device acceptance for all of them.

## Benchmark principles

- [WhatsApp chat filters](https://blog.whatsapp.com/find-messages-faster-with-chat-filters)
  make All/Unread a way to find work quickly. Apply that clarity to UsefulDesk's
  result states; it does not require copying WhatsApp's exact control placement.
- [Apple Messages tracking](https://support.apple.com/en-ng/guide/iphone/iphe9b48b89e/ios)
  distinguishes read/unread scope and returning to all messages. This supports
  a clear recovery action when Unread is empty.
- [Apple Messages search](https://support.apple.com/en-mide/guide/iphone/iph17c111fb6/ios)
  treats search results as a path to the relevant conversation. Keep the result
  list concise; do not turn it into full message history.
- [SafeAreaProvider documentation](https://github.com/appandflow/react-native-safe-area-context/blob/main/docs/docs/api/safe-area-provider.mdx),
  fetched with Context7 during this audit, explicitly permits providers at modal
  roots; insets are relative to the nearest provider. This supports investigating
  F01's modal boundary, not asserting a fix before a native retest.

These are documented benchmark principles, not a fresh hands-on audit of those
apps. Keep UsefulDesk's existing native masters and its India-first terminology.

## Additional validation candidates, not confirmed visual defects

- Conversation identity is always limited to one line. Exercise long names and
  phone numbers at large text sizes before changing its layout.
- Composer text is local component state (`conversation-composer.tsx:150`).
  Verify draft loss on back/re-entry with the non-sending fixture; any draft
  persistence work must be scoped by user/branch/chat and preserve uncertainty
  locks. Persistent drafts and an offline send queue are separate decisions.
- Notification recovery actions in Account have no local loading state. Test a
  slow request before adding pending state; do not grant permissions to test it.
- The launcher showed a blank white app icon. Recheck a current standalone build
  before treating this development-client artifact as a release defect.
- Templates inside an open chat's attachment menu, plus service/invoice prefill,
  are already recorded as pending in the roadmap. They are not newly discovered
  layout bugs and are outside the first repair batch.
